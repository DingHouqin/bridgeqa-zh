# 在线文档网站可行性评估

本文保留评估时点的结论。后续用户已授权实施上传与部署，最新运行和发布方法见 [系统说明](../explorer/README.md) 与 [静态规格](../explorer/specs/06_静态发布与文档.md)。

评估日期：2026-10-07。检查对象为 [现有 explorer](../explorer/README.md)、[服务器](../explorer/server.py)、[前端入口](../explorer/web/index.html) 与 [交互实现](../explorer/web/app.js)。只检查当前工作目录和 origin 地址，没有读取其他分支。本次仅评估，不更改网站代码、发布设置或触发部署。

## 结论

**可行，推荐复用原生 HTML/CSS/JavaScript，增加静态数据导出与文档阅读功能，通过 GitHub Actions 发布到 GitHub Pages。** 不需要 React、Vue、npm 项目脚手架、打包器、数据库或常驻后端。

当前 origin 指向 [DingHouqin/bridgeqa-zh](https://github.com/DingHouqin/bridgeqa-zh)。按 GitHub 项目站点规则，预期首页为 [项目网站目标地址](https://dinghouqin.github.io/bridgeqa-zh/)，章节可采用该地址后加 `#/docs/benchmark-survey/07-scenes` 等稳定路由；这不是已上线地址或已验证的 Pages 配置。GitHub Pages 托管静态 HTML、CSS、JavaScript，项目站点的默认路径包含仓库名，见 [官方说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)。

当前界面依赖 Python 响应，不能直接复制现有前端就上线；改造范围集中在数据加载、路径与文档阅读，题库筛选、证明图、材料角色和干扰展示可复用。

## 推荐的最小方案

### 1. 保留一套前端，导出一份静态发布物

继续维护 [前端目录](../explorer/web/) 与 [数据目录](../data/README.md)，不复制成第二套独立界面。在 [explorer目录](../explorer/README.md) 内新增一个静态导出脚本（拟建），在 [workspace目录](../workspace/) 下生成发布产物（拟建子目录）；无需新增一级目录。

导出脚本用 Python 标准库：调用/复用现有 bundle 组装与验证逻辑，输出静态数据集目录 JSON、逐数据集 bundle JSON，复制前端、文档与下载文件。文件选择用清单；导出前验证题目关联、引用、文档链接和目标路径。发布物自动生成，不手工维护重复数据。

Python 只在本地导出或 Actions 发布阶段运行。在线访问只需要浏览器获取静态文件。以实际导出文件预览网站，也可以用普通静态 HTTP 服务器，无需模拟 API。

目前 pilot 文件合计1,489,844字节，文档目录合计146,019字节；这是源文件大小，不是精确部署包或网络加载体积。当前规模适合按数据集加载完整 bundle，不必立即引入分片索引。后续若显著增长，再按测得的下载与索引耗时拆成题库索引和单题详情。GitHub Pages 当前发布站点上限1GB，见 [官方限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

### 2. 统一站点基路径

当前 [入口](../explorer/web/index.html) 的 `/style.css`、`/app.js`，以及 [交互代码](../explorer/web/app.js) 中的 `/api/...`、`/files/...`、`/specs/...` 都从域名根目录解析。放在仓库子路径下会访问错误地址。

CSS/脚本改用相对路径；fetch、下载、文档和 guide 中的链接统一经过一个站点 URL 函数，基于入口目录解析。bundle 链接也统一输出相对路径。既验证域名根目录预览，也验证 `/bridgeqa-zh/` 子路径；不要依赖手工逐处拼仓库名，也不靠部署时全文字符串替换。

可以让本地服务器同时提供静态数据地址，并让导出器生成同名文件；本地与线上前端读取同一份格式和 URL 约定，避免两套运行逻辑逐渐分叉。旧 API 是否保留由兼容需要决定，不要求线上运行 Python。

### 3. 扩展现有 hash 路由

建议统一采用 `#/overview`、`#/questions`、`#/question/<id>`、`#/guide`、`#/docs/<slug>`。旧的 `#overview` 等地址可保留兼容跳转。

`<slug>` 由文档清单显式登记，映射到真实 Markdown 文件；优先用稳定短名，中文标题或文件名变化不必改变公开 URL。文档页可带 `?section=<标题锚点>`，并与已有 dataset、筛选参数分别处理。未知章节显示恢复入口；刷新、后退与分享链接均由同一个路由器处理。

`#` 后内容不随请求发送给服务器，所以直接打开某章节仍请求项目首页，再由 JavaScript 打开章节。对这类地址不需要服务端 rewrite 或用404页面模拟路由，见 [MDN fragment说明](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment)。

### 4. 文档只维护原始 Markdown

新增一个文档清单（拟建，放在现有 explorer目录），记录标题、分组、slug与源文件。首轮收录项目说明、调研系列、数据说明、评分器评估和设计规格；参考报告独立标为“归档，仅供参考”，不作为设计规范。

建议本地随站点附带一个固定版本的 [markdown-it](https://github.com/markdown-it/markdown-it) 浏览器分发文件及其许可证。它支持浏览器使用，不要求项目安装 npm 或启动打包器。关闭 Markdown 内嵌 HTML，保留表格与代码块；不依赖运行时 CDN，也不用自行写不完整的 Markdown解析器。具体版本、散列和许可证在实施时登记。

内部 Markdown 链接按当前源文件目录解析：已登记文档转为章节路由，JSON/JSONL转为原始文件下载，目录转为说明页；原文标题锚点转为章节定位。外链正常跳转。现有 `thread://` 链接依赖 Codex，应在在线站点显示用途和原始引用，明确它不是可通过普通浏览器打开的在线章节。

先做侧栏分组、文档正文、标题目录、章节链接和源码入口即可。文档搜索若需要，先做标题搜索；不增加远程搜索服务或全文索引构建系统。

### 5. 一条 GitHub Actions 工作流发布

推荐流程为：检出指定发布提交 → Python静态导出与检查 → 上传 Pages artifact → 官方 Pages部署 action。Pages 的 Source 选择 GitHub Actions。官方支持自行准备静态文件并上传发布，不要求采用 Jekyll，见 [发布工作流说明](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)。

工作流放在现有 [.github目录](../.github/) 内的 workflows 子目录（拟建）；明确使用实际发布分支与站点相关路径触发条件，并设置部署并发控制。Pull request 可以只导出验证；获准的发布分支更新才部署。不要读取其他分支获取旧实现，也不需要建立专门维护生成文件的分支。

不建议把当前文档目录直接选成 Pages发布源：前端与数据分散在不同目录，仍需要汇总发布物，而且会把研究文档与生成产物混在一起。仅有一个标准库导出步骤比手工复制整站更可维护，仍不属于复杂构建系统。

## 维护与验收

- 文档更新：改 Markdown，清单已登记的章节自动更新；新增章节补一条清单项。
- 数据更新：改数据与注册项，重新导出；新增数据集同时按既有规则追加固定测试指引章节。
- 界面更新：只改当前前端；本地与线上共用。
- 发布前验证：子路径 CSS/JS/fetch、文档相对链接、标题锚点、章节刷新与历史导航、数据下载及UTF-8文件名。
- 回归现有概览、全部标签筛选、证明图、替代支持、反事实、无材料、固定guide与手机布局；比较本地与静态导出数据一致性。

现有服务器设置的 HTTP 安全与缓存响应头不保证在 Pages 上原样保留；应按静态环境检查，不把本地服务器头部测试直接当线上验收。首轮无需 Service Worker，减少版本更新时的缓存排查负担。

## 尚待确认的发布条件

本次确认了本地仓库根与 origin 地址，尚未查询 GitHub仓库可见性、Pages是否启用、现有线上内容、账户套餐、Actions及部署权限。GitHub Free支持公开仓库的 Pages；私有仓库的可用性取决于套餐，配置发布源需要相应仓库权限，见 [官方配置说明](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。这些影响是否能发布，不改变静态迁移在技术上的可行性。

完整 explorer 的发布包将包含标准答案和参考证明，因为详情展示本身依赖这些数据。它可以作为当前开发候选集的公开审阅网站，不能充当隐藏测试集或受控评测后台。发布清单应只收录预定内容，不把临时日志、实验输出或整个工作目录自动复制到站点。

下一步实现范围可以限定为：静态导出、统一路径、文档阅读与路由、发布工作流和静态浏览器验收。当前只形成可行性方案，没有创建导出目录、修改运行代码或发布网站。
